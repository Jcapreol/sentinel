## Calibration saturation incident — zero-evidence and conflicting-evidence
messages defaulted to a confident wrong verdict (2026-07-28) — RESOLVED same day

- **The real isotonic fit (400 samples, committed 2026-07-28) turned out to be a
  hard 0/1 step function with no middle output** [src/sentinel/triage/scoring.py,
  worker.py] — every raw_score below approximately 0.41 calibrated to exactly 0.0,
  every score above it to exactly 1.0, with nothing in between, ever. This defeated
  the entire deferral safety net: the neutral prior (raw_score=0.5, i.e. genuinely

  failing tests on both Python 3.10 and 3.12), root-caused before any fix was
  attempted. **Fixed with two structural pre-calibration deferral gates in

- **Gmail pagination can silently drop already-fetched messages if `history.list()` 404s on a page AFTER page 1 already succeeded — Medium severity, pre-existing Epic 1 scope (`poll_new_messages` predates Story 2.2; the story only added `extract_email_content` to this file).** [src/sentinel/triage/ingest.py — `poll_new_messages`] Traced directly: inside the `while True:` pagination loop, a 404 on `history.list()` (Gmail's documented "historyId expired" response) returns `[], current_history_id` unconditionally — discarding whatever messages the loop's `messages` list already accumulated from earlier, successfully-fetched pages, and advancing the checkpoint (`current_history_id`, captured via `getProfile()` before pagination began) past them, so they are never retried on a future poll either. A 404 on the FIRST page (the common case — `since_history_id` itself has expired) is handled correctly by this same code (nothing was accumulated yet, so nothing is lost). The bug is specific to a 404 on a LATER page, which requires the history data for the fixed `since_history_id` to become unavailable partway through an active, multi-page pagination sequence — rarer, but real, and this directly contradicts the module's own stated design goal (`ingest.py`'s module docstring): "silently dropping a message is worse than processing it twice." ## Live-data observations (unconfirmed — pending larger sample) (2026-08-08)

Both observations below came from analyzing the first 56 records the live Gmail triage pipeline (personal OAuth mode, Story 4.3) collected. They are evidenced observations to revisit as more live data accumulates — **not scoped stories, not confirmed bugs, and no scoring code has been changed as a result.**

- **Observation 1 — Watchman precision problem (strongly suggested).** Watchman appears to over-trigger malicious findings on legitimate commercial email. In the first 56 live records, the top ~12 by accumulated malicious weight are all legitimate senders (DoorDash, Workday, Amazon Health, ZipRecruiter, SoFi, Costco, DICK'S), each accumulating 0.5–0.95 malicious weight from Watchman flagging normal e-commerce behavior: tracking parameters, urgency language, recipient email present in unsubscribe links, ESP subdomain routing. Example: a legitimate DICK'S marketing email (sender `DSG@e.dcsg.com` — `dcsg.com` is DICK'S real corporate domain) got six malicious Watchman findings and was only saved from a bad verdict by header-auth pass weight. Potential direction (not committed): make Watchman findings more specific, or down-weight generic marketing patterns. Evidence: `hunt_phishing.py` output over the live DB.

- **Observation 2 — auth-passing-phishing blind spot (hypothesized, UNCONFIRMED).** Original hypothesis: SPF+DKIM+DMARC pass (1.05 combined benign weight) structurally exceeds Watchman's max malicious contribution (0.7), so an auth-passing phishing email can never be flagged by content analysis alone. **However, closer inspection found no confirmed phishing in the 56-record sample to demonstrate this** — the email originally thought to prove it (DICK'S) turned out to be legitimate. So this remains a structural hypothesis about the scoring model, not an observed failure. Also note: header-auth is currently load-bearing as the counterweight to Watchman's over-triggering (Observation 1 above), so any fix that lowers header-auth weight must account for that interaction, or it will spike false positives on legitimate mail. Revisit specifically when a real phishing email lands in the live inbox and can be checked against the model's verdict. One near-miss: a single record with FAILED auth and a garbled-encoding sender still scored Benign/0.000, but is likely a misconfigured legitimate sender, not confirmed phishing.

Both observations rest on a small, unrepresentative sample (56 emails, a few days, one personal inbox) and should be re-evaluated once the pipeline has accumulated a few hundred records across more senders.
