## Calibration saturation incident — zero-evidence and conflicting-evidence
messages defaulted to a confident wrong verdict (2026-07-28) — RESOLVED same day

- **The real isotonic fit (400 samples, committed 2026-07-28) turned out to be a
  hard 0/1 step function with no middle output** [src/sentinel/triage/scoring.py,
  worker.py] — every raw_score below approximately 0.41 calibrated to exactly 0.0,
  every score above it to exactly 1.0, with nothing in between, ever. This defeated
  the entire deferral safety net: the neutral prior (raw_score=0.5, i.e. genuinely
  absent evidence) calibrated to 1.0, meaning a message with zero real evidence —
  no SPF, no DKIM, no DMARC — got a confident Malicious verdict. Caught by CI (5
  failing tests on both Python 3.10 and 3.12), root-caused before any fix was
  attempted. **Fixed with two structural pre-calibration deferral gates in
  process_message**, both independent of whatever the calibration curve outputs,
  both proven via regression tests that mock apply_calibration to always return
  1.0 (the worst case): (1) all-neutral evidence (no real signal found at all)
  routes directly to Deferred, mirroring the existing FetchFailed precedent; (2)
  raw_score landing near the neutral prior (weak-but-present, near-cancelling
  evidence, e.g. dmarc=pass vs spf=fail) also routes to Deferred, checked on the
  RAW score since no deferral_band on the calibrated score could ever catch it
  against this curve. Framed in code comments as a stopgap tied to the corpus
  lacking ambiguous/conflicting-evidence training examples (see the caveat entry
  above) — the real long-term fix is broadening the calibration corpus with
  genuinely ambiguous examples so the model learns a real middle, not just relying
  on these safety nets indefinitely. 518/518 tests passing, both fixes committed
  and pushed.
